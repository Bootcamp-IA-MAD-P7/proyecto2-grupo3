# Retrospectiva del Proyecto

## Proyecto

Sistema de Gestion para Escape Rooms.

## Equipo

Grupo 3.

## Periodo revisado

Proyecto 2 completo, con especial foco en el Sprint 1 - MVP Esencial y el Sprint 2 - Mejora, Experto y Cierre.

## Objetivo inicial

Desarrollar una API REST y una base de datos SQL para digitalizar la gestion de un negocio de escape rooms, sustituyendo procesos manuales y preparando el negocio para crecer.

## Que salio bien

- Se definio un negocio concreto y un contexto realista.
- Se creo un tablero Jira con epicas, historias, subtareas y responsables.
- Se trabajo con GitHub, ramas y pull requests.
- Se implemento una API REST con FastAPI.
- Se modelo una base de datos relacional con entidades conectadas.
- Se anadio documentacion interactiva con Swagger/OpenAPI.
- Se incorporaron tests automatizados para endpoints principales.
- Se desarrollo un frontend web para visualizar y gestionar la aplicacion.
- Se avanzo hacia niveles superiores del briefing con Docker, Azure, WebSockets e integracion externa.
- Se mantuvo documentacion de seguimiento mediante dailys.

## Que se podria mejorar

- Congelar `main` antes de los ultimos dias para evitar conflictos cerca de la entrega.
- Definir antes una convencion comun para ramas, PRs y revisiones.
- Separar con mas claridad tareas funcionales, tareas de documentacion y tareas de despliegue.
- Validar antes los cambios grandes en frontend o despliegue antes de mergearlos.
- Mantener tests y rutas sincronizados desde el inicio.
- Documentar decisiones tecnicas importantes justo cuando se toman, no al final.

## Dificultades encontradas

- Diferencias de nivel tecnico dentro del equipo.
- Conflictos de Git y PRs con cambios grandes.
- Ajustes de despliegue en Azure y variables de entorno.
- Necesidad de coordinar cambios funcionales con documentacion y Jira.
- Riesgo de introducir cambios de ultima hora cerca de la entrega.

## Aprendizajes

- SCRUM ayuda a ordenar el trabajo, pero requiere disciplina diaria.
- Las dailys y comentarios en Jira facilitan reconstruir el proceso del proyecto.
- Git permite recuperar estados anteriores, pero conviene evitar merges grandes sin revision.
- Las variables de entorno deben estar correctamente definidas en despliegue y no depender del entorno local.
- La documentacion final es parte del producto, no solo un anexo.
- La validacion de tests y despliegue debe formar parte del cierre de cada sprint.

## Acciones de mejora para futuros proyectos

- Crear una guia inicial de trabajo con Git y PRs para todo el equipo.
- Establecer una rama de desarrollo y proteger `main`.
- Hacer revisiones tecnicas periodicas antes de fusionar cambios.
- Mantener README y Jira actualizados durante el proyecto, no solo al final.
- Reservar un bloque especifico para estabilizacion antes de la entrega.
- Evitar cambios funcionales no imprescindibles en las ultimas horas.

## Conclusion

El proyecto permitio construir una solucion funcional para la gestion de escape rooms y trabajar competencias clave de backend, base de datos, testing, documentacion, Git, SCRUM y despliegue. Aunque hubo dificultades de coordinacion y ajustes de ultima hora, el equipo consiguio avanzar desde un MVP esencial hacia una solucion mas completa con frontend, Docker, Azure e integraciones avanzadas.
